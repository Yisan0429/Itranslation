# Repository Guidelines

## Project Structure & Module Organization

Itranslation is a Python 3.11+ book translation tool with both GUI and CLI entry points. Top-level modules are organized by pipeline stage:

- `desktop.py`: tkinter desktop UI.
- `translate_book.py`: command-line entry point and orchestration.
- `extractor.py`, `chunker.py`, `translator.py`, `assembler.py`: extraction, semantic chunking, LLM translation, and output assembly.
- `consistency.py`, `kg_builder.py`, `vector_store.py`: terminology checks, preread knowledge graph, and optional RAT retrieval.
- `config.py`: runtime configuration handling.

Runtime directories are `input/`, `output/`, `chunks/`, `cache/`, `final/`, `vector_store/`, and `models/`. They are kept in git with `.gitkeep`; generated contents are ignored.

## Build, Test, and Development Commands

- `uv sync`: install core dependencies from `pyproject.toml`.
- `uv sync --extra vision`: add marker-based visual PDF extraction dependencies.
- `uv sync --extra rat`: add ChromaDB and sentence-transformer retrieval dependencies.
- `uv run python desktop.py`: launch the GUI.
- `uv run python translate_book.py input/book.pdf --genre literature`: run a CLI translation.
- `uv run python -m compileall .`: perform a quick syntax check across Python files.

There is no separate build step; outputs are generated by the GUI or CLI into `final/`.

## Coding Style & Naming Conventions

Use standard Python style: 4-space indentation, `snake_case` for functions and variables, `PascalCase` for classes, and clear module-level constants where appropriate. Keep pipeline logic in the stage-specific module instead of expanding entry points with unrelated behavior. Prefer small helper functions over duplicated parsing or file-handling code.

## Testing Guidelines

No automated test suite is currently configured. Before submitting changes, run `uv run python -m compileall .` and exercise the touched path with a small input file where possible. When adding tests, place them under `tests/` using `test_<module>.py` naming and prefer focused fixtures for PDF/EPUB/TXT/MD parsing behavior.

## Commit & Pull Request Guidelines

Recent history uses a mix of Conventional Commit prefixes and release-style messages, for example `feat: ...`, `refactor: ...`, `docs: ...`, and `v1.0.1: ...`. Prefer `type: concise summary` for normal changes.

Pull requests should include the user-facing behavior change, commands run, any optional extras needed to reproduce, and screenshots for GUI changes. Link related issues when available.

## Security & Configuration Tips

Never commit `config.json`, API keys, source books, generated translations, caches, vector stores, or downloaded models. These are intentionally ignored by `.gitignore`; keep only placeholders such as `.gitkeep` in version control.
